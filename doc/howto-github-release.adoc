= How-to: Einen GitHub-Release manuell anlegen
:toc:
:sectnums:

== Zweck und Geltungsbereich

Dieses How-to beschreibt ausschließlich das manuelle Anlegen eines GitHub-Releases im GitHub-Repository `j-specman/specman`.

Der Ablauf gilt für:

* ein neues Release auf dem aktuellen Hauptbranch `master` und
* die nachträgliche Veröffentlichung einer älteren Version.

Die Release-Artefakte müssen vor dem Anlegen des GitHub-Releases bereits erstellt und geprüft worden sein. Wie die Artefakte gebaut oder getestet werden, ist nicht Bestandteil dieses How-tos.

== Voraussetzungen

Vor dem Öffnen des Release-Dialogs müssen folgende Informationen und Dateien vorliegen:

. Schreibberechtigung für das Repository `j-specman/specman` und Zugriff auf dessen Releases-Bereich.
. Die eindeutige Versionsnummer, zum Beispiel `1.3.2`.
. Der passende Commit im Repository.
** Für ein neues Release ist das der geprüfte Release-Commit auf `master`.
** Für ein älteres Release muss der historische Release-Commit anhand der Git-Historie eindeutig bestimmt worden sein.
. Der Tagname im Format `v<version>`, zum Beispiel `v1.3.2`.
** Existiert der Tag bereits, muss er auf den passenden Commit zeigen.
** Existiert er noch nicht, muss ein passender Target-Branch vorhanden sein, dessen aktueller Stand dem Release-Commit entspricht. GitHub legt den neuen Tag beim Erstellen des Releases auf diesem Target an.
. Die bereits geprüften Release-Artefakte. Dateiname und enthaltene Version müssen zum Release passen.
. Fertige Release Notes mit den wichtigsten Änderungen, bekannten Einschränkungen, Upgrade-Hinweisen und einer Liste der enthaltenen Dateien.

Vor dem Veröffentlichen muss außerdem feststehen, ob es sich um ein reguläres Release oder ausdrücklich um eine Vorabversion handelt.

== GitHub-Release anlegen

. Das Repository `j-specman/specman` auf GitHub öffnen.
. **Releases** öffnen.
. **Draft a new release** auswählen.
. Unter **Choose a tag** den vorhandenen passenden Tag auswählen oder einen neuen Tagnamen im Format `v<version>` eingeben und **Create new tag** auswählen.
. Wenn ein neuer Tag angelegt wird, als Ziel (**Target**) den Branch auswählen, dessen aktueller Stand dem zuvor bestimmten Release-Commit entspricht. GitHub bietet im Release-Dialog die Auswahl eines Branches an, nicht die freie Auswahl eines beliebigen Commits.
. Als Titel des Releases `Specman <version>` eintragen, zum Beispiel `Specman 1.3.2`.
. Die vorbereiteten Release Notes in das Beschreibungsfeld einfügen.
. Die vorbereiteten Artefakte in den Bereich für Release Assets ziehen oder über die Dateiauswahl hochladen.
. Falls GitHub automatisch Release Notes erzeugt, diese nur als Entwurf verwenden und fachlich prüfen. Sie ersetzen nicht die Informationen zu Artefakten, Einschränkungen und Upgrade-Hinweisen.
. **This is a pre-release** nur aktivieren, wenn die Version ausdrücklich eine Vorabversion ist.
. Solange noch geprüft wird, **Save draft** wählen. Erst nach der Kontrolle **Publish release** auswählen.

== GitHub-Release prüfen und veröffentlichen

Vor dem endgültigen Veröffentlichen prüfen:

* Der Titel des Releases enthält die richtige Version.
* Der Tagname entspricht exakt der Version und folgt dem Format `v<version>`.
* Der Tag zeigt auf den vorgesehenen Commit. Bei einem neu angelegten Tag dazu den ausgewählten Target-Branch und anschließend die Commit-Ansicht des Tags prüfen.
* Die Release Notes beschreiben das tatsächlich veröffentlichte Release.
* Alle erwarteten Assets sind vorhanden und sinnvoll benannt.
* Das Release ist nur dann als Pre-release markiert, wenn dies beabsichtigt ist.

Nach **Publish release** die fertige Release-Seite öffnen und mindestens Folgendes kontrollieren:

. Das Release ist über den richtigen Tag erreichbar.
. Die Assets lassen sich herunterladen.
. Die heruntergeladenen Dateien sind nicht leer und entsprechen den vorbereiteten Dateien.
. Versionsnummer, Release Notes und Asset-Namen stimmen überein.

Einen veröffentlichten Tag nicht nachträglich auf einen anderen Commit verschieben. Bei einem falschen Commit oder einem fehlerhaften Asset das Release nicht stillschweigend umdeuten. Stattdessen das Release nachvollziehbar korrigieren oder zurückziehen und erforderlichenfalls eine neue Version mit einem neuen Tag veröffentlichen.

== Ältere GitHub-Releases nachträglich veröffentlichen

Für ein älteres Release wird derselbe GitHub-Ablauf verwendet. Vor dem Anlegen des Releases ist jedoch zusätzlich zu prüfen:

. Der historische Commit ist eindeutig identifiziert.
. Der Tag `v<version>` existiert noch nicht oder zeigt bereits auf genau diesen Commit.
. Die hochzuladenden Artefakte gehören nachweisbar zu diesem Commit und dieser Version.
. Nicht mehr eindeutig zuordenbare oder nicht vertrauenswürdig rekonstruierte Dateien werden nicht hochgeladen.

In den Release Notes muss kenntlich gemacht werden, dass das Release nachträglich angelegt wurde. Dabei sollten der historische Versionsstand und das Datum der nachträglichen Veröffentlichung genannt werden. Die automatische Erstellung von Source-Archiven durch GitHub ersetzt auch bei älteren Versionen keine verifizierten Release-Artefakte.
