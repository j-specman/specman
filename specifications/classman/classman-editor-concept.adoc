# Classman Diagram Editor: Concept and Functional Description

*Status: updated 2026-11-22. Describes what is built, what was decided and why, and what is open. It is kept up to date with every step of the editor, because it is the source for the Specman system use cases which will be derived from it later: the behavior is hard to read back from the code. Where something is planned and not built, it says so.*

## Goal
Class diagrams are shown in the Aktogramm, painted with Graphics2D, and are edited in a window of their own: creating, moving, renaming and deleting every kind of element, without editing the diagram source by hand. The editor is later the core of Classman itself. It must not depend on Specman, and the interface between the two stays narrow.

The source text of the diagram (see `ClassDiagram_V001.g4`) stays the single persistent representation. The editor reads it, shows it as a scene, and writes a changed source after each completed operation.

### Why a Window of its Own
The first idea was to edit in place, in the Aktogramm, with a palette that replaces the step palette. It was tried (see git branch `classman-inplace-experiment`) and dropped for two reasons:

* While editing, the diagram can't be scrolled and zoomed independently of the Aktogramm around it. A diagram often has to be shown shrunk to fit the document, but is edited at a readable size.
* The pieces of Specman and Classman would have grown into each other: the editor needs the tool bar, the focus handling, the undo manager and the layout of the Aktogramm.

## Structure
[cols="1,3"]
|===
|Part |Responsibility

|`classman.render` |Display. Builds an immutable `Scene` from the model with the pure layouters, `SceneGraphicsPainter` paints it with Graphics2D, `SceneSvgWriter` writes it as SVG. No dependencies on Specman.
|`classman.model` |The model of a diagram, its parser and serializer, and the logic which changes the model: accepting, rejecting and renaming change marks, deleting, changing texts and attributes.
|`classman.editor` |The editor: the window, the canvas with its tools, the palette, the text field. No dependencies on Specman. It works on the source text and reports its changes through the interface below.
|`specman.editarea.image.classman` |The thin adapter in Specman. The edit area shows the diagram as a `Picture` (`ScenePicture`), opens the editor window on a double click, and takes over the changes of the source as undoable edits.
|===

The rule `classman.*` never imports `specman.*` is checked by a test, so that it holds. Where the editor needs something which only the host knows, the host provides it through the interface.

### Display
The Aktogramm shows the diagram with the same painter as the editor window, so both show the same picture. The painter keeps the marks of changes recognizable when the diagram is shown small, see <<Display of Changes>>.

SVG is only needed for the PDF export. There the scale between the Swing picture and the PDF is known, so the SVG can be asked for the marks at that scale (`Picture.svg(scale)`, with the same rule as the painter, shared by both). This is a separate step, not built yet.

### Interface between the Editor and Specman
The interface is small on purpose. Four things pass it:

* *Initiation:* Specman opens the editor for a diagram with its source and waits until the window is closed.
* *Synchronization:* After each completed operation, the editor reports the new source, `sourceChanged(source)`. Specman puts it into the edit area, which shows the diagram anew right away. The window is modal, so nothing else changes the source while the editor is open: Specman never has to push a source into a running editor. This is the reason for the window being modal.
* *History:* The editor asks the host for the current source, and to undo and redo, see <<Undo and Redo>>.
* *Context:* what the editor needs to know from the host and can't know by itself: whether changes are tracked and by which change set, so that it writes the `change(...)` and `was(...)` marks; the colors of the change sets (strong, pale, and for blue a special selection color); the language.

The texts of the editor come from a resource bundle of Classman, the host passes the language. Specman's own classes (`Messages`, `SpecmanIcons`) are not used by the editor.

## Editor Window
There is one window, and it is modal: While it is open, the rest of Specman can't be operated. So there is never more than one editor, and nothing else changes the diagram while it is edited. The window needs no Done button, closing it is leaving the editor.

* *Opening:* A double click on a Classman diagram in the Aktogramm opens the window. If the source can't be parsed, or refers to an element which the diagram doesn't have, the source editor opens instead, where the user can repair the text. The source editor stays available in the context menu of the diagram.
* *Size:* The window is as large as the whole diagram, the palette and the window decorations need, but at least 500 x 350 pixels. There is no fixed upper limit, because the user wants to see the whole diagram where the screen allows it (an earlier limit of 1200 x 800 pixels was dropped for this). A diagram larger than the screen is cut to the usable part of the screen (without task bar), and scrolls. Where it is cut in one direction, the window gets the width of the scroll bar of the other direction in addition, so that no second scroll bar becomes necessary. The size is worked out once, when the window opens, for the diagram at 100 % zoom. Zooming, adding or moving boxes afterwards doesn't change the size of the window; the user can resize it as usual.
* *Position:* The window is centered on the visible part of the diagram in the Aktogramm. It is then pushed completely into the usable part of the screen of the owner window. Being seen completely wins over being near. The window doesn't remember its position or size.
* *Scrolling and zooming:* with the mouse wheel and Ctrl + mouse wheel. The zoom goes from 25 % to 400 %, in steps of 10 %. If the diagram is smaller than the window, the canvas fills the window, so there is room to drop things where the diagram has none yet.
* *Esc:* does the first of these which applies: puts a box or a point of a relation back which is being dragged; takes the selection away; closes the window. While a text is typed, Esc belongs to the text field.
* *Keys:* Delete deletes the selected box, Ctrl+Z undoes, Ctrl+Y and Ctrl+Shift+Z redo. While a text is typed, these keys belong to the text field.

### Palette
The palette is a vertical tool bar at the left edge of the window, built like the step palette of Specman: buttons with an icon and a text, or with an icon only, which the user switches with the button at the bottom. The editor has its own preference for that. The most important element comes first, at the top: the class.

#### Buttons with Variants (planned)
The number of element kinds will grow, so related kinds share one button. A button with variants shows the icon and the text of the variant it creates, and has a small arrow at its corner which opens a menu with the other variants. Choosing a variant makes it the current one of the button; using the button creates it. The last choice is remembered.

Variants are grouped if they are used with the same gesture and differ in one property only:

[cols="1,2,1"]
|===
|Button |Variants |Gesture

|Class |class, interface, enum |drag onto canvas
|Note |note, association class (open) |drag onto canvas
|Association |association, aggregation, composition |tool
|Inheritance |extends, implements |tool
|===

Interface and enum are keywords of their own, because their content differs from a class: A class has attributes, an enum holds only its values, which are entered like attributes without a type, and an interface has no attributes. See <<Consequences for the Format>>.

### Width of a Class Box
* *Without `width=`* the box is as wide as its widest part: the longest line of the name, the stereotype, the tagged values or an attribute (at least `DiagramStyle.MIN_BOX_WIDTH`). Nothing is wrapped or cut off. The box grows with long attributes and shrinks again when they get shorter. The editor creates classes this way.
* *With `width=`* (set by the user by dragging, see below) the width stays, whatever the content is:
** The *class name* wraps at spaces. The box is at least as wide as the longest single word of the name.
** The *stereotype*, the *tagged values* and every *attribute* never wrap. They stay one line and are cut off at the right end of the box. A line break in them (only a hand-written source can have one) is shown as a blank.
** The marks of changes (backgrounds, strikes) cover only what is shown.
* *Changing the width:* there are no handles. Where the mouse is at the left or right side of a class, along its whole height and 4 pixels of the screen to both sides of the border, the cursor becomes the horizontal resize cursor. The class needn't be selected. A press there selects the class, and dragging gives it a width of its own (`width=N`): the opposite side stays where it is, so dragging the left side moves the box. The box can't be made narrower than its layout allows, which is the longest word of its name; the stored width is the shown one. The class gets a position of its own (`at(x, y)`) if it had none, and so do the other classes and notes which are stacked, so that they stay where they are (like with moving). Esc during the drag puts everything back. One drag is one operation, one undo step. Like moving, resizing is never marked as a change.
* *Back to the automatic width:* the entry *Automatic width* of the context menu of the class. It is checked while the class has no width of its own and can't be chosen then; dragging a side switches it off, choosing it removes `width=`. One operation.
* *Not built:* the same for association classes, a minimum width for the whole class (stereotype, attributes) beyond the name.
* *Planned:* a cut-off text ends with `...`, so the user sees that there is more. The field for typing an attribute is wrapped at the width of the box for now; it shows the whole text.

### Width of a Note
* *Without `width=`* the note is as wide as its longest line, but at most `DiagramStyle.NOTE_MAX_AUTO_WIDTH` (240). A longer text is wrapped at that width and the note grows downwards instead of becoming an endless strip. Its text never wraps in the middle of a word, so the note is at least as wide as the longest word.
* *With `width=`* the text is wrapped at that width, whatever it is. A very wide note is the decision of the user, like a very narrow one.
* *Changing the width* works like for a class: dragging the left or right side gives the note a width of its own, the opposite side stays, and a note which is stacked gets a position, so that all boxes stay where they are. The note can't be made narrower than its longest word. One drag is one undo step, Esc puts everything back, and the width is never marked as a change.
* *Back to the automatic width:* the right mouse button on a note selects it and opens a menu with the one entry *Automatic width*, the same check item as in the menu of a class.
* *Not for classes:* a class has no upper limit for its automatic width. Its name can't wrap, and cutting off an attribute which the user never asked to shorten would hide content. Whether that feels right has to show in practice.

### Creating Elements
Specman's step buttons are drag sources: The user drags a step onto the diagram. The palette follows this for everything that is a single box.

*Built, the class:*

* The user presses the class button and drags. A ghost of the class follows the mouse. The class is created where the mouse is released, if that is inside the canvas of the window. Released anywhere else, nothing happens.
* The drop point becomes the top left corner of the new class: `at(x, y)` in diagram coordinates, rounded to whole pixels, whatever the zoom is.
* The field for the name opens right after the drop, over the name row of the new class, empty. The class has no made-up name. Return with a name creates the class; Return with an empty name, Esc, or leaving the field takes the class away again. Until then the class is part of the picture (selected, with its box) but not of the diagram: nothing is reported to the host and there is no undo step. While the name is typed, the box is `DiagramStyle.NEW_BOX_WIDTH` (140) units wide, so that the empty field (120 pixels at 100 % zoom) lies completely inside it. That width is only for typing: the created class has no `width=`, so it is as wide as its content, see <<Width of a Class Box>>. Fields have their minimum width in proportion to the zoom, like their font. Class names need not be unique.
* It gets an ID: 8 hexadecimal characters, different from all IDs in the diagram.
* If changes are tracked, it gets `change(added, <change set>)`.
* The new class is selected. Creating it with its name is one operation, one undo step. While changes are tracked, the name needs no mark of its own: a class which a change set has added is named plainly.

*Built, the note:*

* The note button is dragged onto the canvas like the class button, and the drop point becomes the top left corner of the note (`at(x, y)`).
* The field for the text opens right after the drop, empty, in the new note. The note has no made-up text. Return with a text creates the note; Return with an empty text, Esc, or leaving the field takes the note away again, without an operation. While the text is typed, the box is `DiagramStyle.NEW_BOX_WIDTH` wide, like a class; the created note has no `width=`, so it is as wide as its text, but at most as wide as <<Width of a Note>> says.
* It gets an ID and, if changes are tracked, `change(added, <change set>)`; its text needs no mark of its own. The new note is selected. One operation, one undo step.
* A note is not attached to anything when it is created. How a note gets attached is an open point.

*Built, the association (first relation, as a vertical slice):*

* A relation needs two ends and is a *tool*, not a drag source. The user clicks the button of the palette, which stays pressed, and the cursor on the diagram becomes a crosshair. A press on a class and a drag to another class draws the relation. A press which is not on a class (or at most 4 pixels of the screen away from one) starts nothing.
* While the mouse is dragged, a line in the color of the selection runs from the center of the first class to the mouse. Where the mouse is on a class, or at most 6 pixels of the screen away from it (the closest one, the topmost one if equal, like for hanging an end), that class is framed like a selected box and the line ends at its center. Only classes can be ends, no notes or association classes.
* Released on a class, the association is created: directed (open arrowhead at the target), from the first to the second class, a straight line without a route, no label, no multiplicities, a new ID. If changes are tracked, it gets `change(added, <change set>)`. A class which has no ID gets one, because a relation refers to its classes by ID. The new relation is selected, so its places for label and multiplicities are there right away, and the tool is put away (one-shot). One operation, one undo step.
* Released on no class, nothing is created and the tool stays armed, so the user can try again. Esc stops a drawing which is going on; another Esc, or a click on the pressed button, puts the tool away. A press on a class without a drag creates nothing.
* The same class can be both ends (a loop), but only after the mouse has been away from the class once, so that a shaky click on a class doesn't draw one.
* While the tool is armed, classes can't be selected, moved or edited, and double clicks do nothing.

*Planned:*

* Boxes (interface, enum) are dragged onto the canvas in the same way.
* *The other relation types* (aggregation, composition, inheritance, implementation) work like the association, with the buttons and variants of <<Buttons with Variants (planned)>>. Inheritance and implementation have no multiplicities and always an arrowhead.
* *Everything within a box* has no button: Attributes, enum values, stereotypes and tagged values are created by the context menu of the class and edited in place, labels and multiplicities by their places on a selected relation, see <<Attributes>> and <<The Context Menu of a Class>>.

## Selecting
* A mouse press on a box selects it. Boxes are classes, notes and association classes. Where boxes overlap, the one drawn on top is selected. A press on empty canvas, or on anything which isn't a box or a relation, takes the selection away.
* *Relations:* A press on the line of a relation selects it, if it is at most 4 pixels of the screen away from the line, whatever the zoom is, so that the line can be hit when the diagram is shown small. Where a box and a line are both hit, the box wins: a press next to the border of a box, where lines start, selects the box.
* A selected relation is shown by its line and the marks at its ends (arrowhead, triangle, diamond), which are drawn 2.5 units wide instead of 1, with round corners so that the sharp tips of the marks reach only about 1.25 units into the box they point at. It has no frame. Each part keeps its place in the order of drawing, so the marks stay above the line. A relation can be deleted with the Delete key, see <<Deleting>>. It can't be moved or dragged: it has no position.
* A selected relation also shows its points: small circles (9 pixels of the screen wide, white, outlined in the color of the selection, the same size at every zoom) where its line starts, at each waypoint, and where it ends. They are the grips for moving the points, see below. A relation without a route has the two ends, a loop its five points.
* *Moving a point:* A press on a handle of the selected relation, or of a relation which the press selects, and a drag (after 3 pixels, like for a box) moves the point; it is one operation, one undo step, Esc puts it back. The point follows the mouse by the distance which it was moved, so it doesn't jump to the mouse. A *waypoint* goes wherever the mouse takes it, in whole pixels. *Snapping:* so that vertical and horizontal lines are easy to get, a point which is dragged snaps to the line of its neighbors, the points before and after it in the line (the ends of the line count as neighbors too): if its x is at most 6 pixels of the screen (at every zoom) away from the x of a neighbor, it takes that x, so the part of the line to the neighbor is vertical; the same for y and horizontal. x and y snap on their own, so a point can snap to one neighbor in x and the other in y, which gives a right angle, and where both neighbors are close the closer one wins. The *start and end* of the line slide along the border of their class, also around its corners to another side: they are at the point of the border which is closest to the mouse, after snapping to their neighbor, and can be hung onto another class, see below. There is no guide line which shows the snapping (decided: it isn't needed), and no key which switches it off so far.
* *Hanging an end onto another class:* While an end of the line (start or end) is dragged, it hangs on the class which the mouse is on or at most 6 pixels of the screen away from, the closest one, and the topmost one where several are equally close. It sits at the point of that class's border which is closest to the mouse (after snapping), the waypoints stay. The class which it is going to hang on is framed like a selected box, as long as it is not the class the end was hanging on when the drag started. Where the mouse is on no class, the end stays on the class it caught last (at the start, its own), so the line doesn't jump back and forth between classes while the user drags over several; to take it back to its own class the mouse has to go onto that class again, or the user presses Esc. Only classes can be targets, no notes or association classes. The same class at both ends is possible (a loop). Esc puts the classes, the route and the points back. The relation keeps its ID, its association class and its attached notes. One operation, one undo step.
* *Not while changes are tracked:* Hanging a relation onto another class is a change of what it connects, which the format has no mark for, and a rejected change couldn't bring back the old class and anchor. So while changes are tracked an end stays on its class and can only slide along its border. This is decided and final, not a gap: the user deletes the relation and adds a new one, so that the change is visible as one. A relation which the tracked change set has added itself is no exception. A relation without a route gets one with the first move, which runs along its line as it is now (see below), and loses it again if the drag is cancelled. A press on a handle without a move changes nothing. Not marked as a change.
* A press on a handle of the selected relation (4 pixels of the screen around its center, like the line) keeps the relation selected, also where a box lies below the handle: the handles are above everything.
* *Deleting a waypoint:* A double click on a waypoint of the selected relation deletes it, and the relation stays selected. The handles at the ends are no waypoints and stay, and a relation without a route has no waypoints (a loop only has its automatic points). With the last waypoint the route is gone, and the relation runs automatically again, from center to center. Changing a route is never marked as a change, so this is the same with and without change tracking. One operation, one undo step.
* *Adding a waypoint:* A double click on the line of the selected relation puts a waypoint at the closest point of the line, so the line keeps its shape, and between the right neighbors. Adding and deleting are both a double click, so they feel alike: on the line it adds, on a handle it deletes. The first press of the double click selects the relation, so a double click on the line of a relation which isn't selected yet selects it and adds the waypoint. The new point has a handle at once. Nothing happens on a handle, a box or a text of the relation, where a double click means something else (see <<Editing Texts>>). A relation without a route gets one for its first waypoint, which runs along its line as it is now: the ends become anchors on the sides of the classes where the line touches them (side and offset in whole pixels), the inner points of its path, as of a loop, become waypoints. From then on the ends no longer follow the line from center to center when a class is moved, as for every route. Not marked as a change, one undo step.
* Attributes and the lines from notes to their targets can't be selected yet.
* A selected box has a frame: 2 pixels wide, 4 pixels away from the box, always the same size on the screen whatever the zoom is, and translucent. Its color is the focus color of the look and feel (blue). Boxes which a change set with blue marks has marked get a black frame instead, because blue marks hide a blue frame.
* A class which has just been created is selected. After undo or redo nothing is selected, because the diagram is read anew.
* A box can be moved, deleted and have its texts edited only while it is selected, see below. The texts of relations are the exception.

## Moving
* A press on a box selects it, and a drag moves it. The drag starts after the mouse has moved 3 pixels, so that a click is never a move.
* While dragging, the diagram is laid out anew with the box at the mouse. Nothing is reported to the host until the mouse is released. The release is one operation and one undo step.
* Esc during the drag puts the box back and ends the drag.
* *Freezing:* Boxes without a position (`at(x, y)`) are stacked automatically. As soon as one box is moved, all boxes without a position get the position where they stand now, so that the others don't jump when the stack loses a member. Only the dragged box moves.
* An association class belongs to its relation and stands automatically next to its line. Dragging it gives it its own position. The association classes of other relations stay automatic.
* The canvas keeps its origin during the drag, otherwise it would follow the box and the mouse could never get ahead of it. Dragging to the edge of the window scrolls.
* *Known limits:* A box which is dragged left of or above the top left of the diagram is cut off until the mouse is released. The waypoints of routes, and of the dashed lines of notes, are absolute points and don't move with the box. The user moves them by their handles, see <<Selecting>>; no operation moves them along with a box. There is no move cursor and no grid snapping.

## Deleting
* The Delete key deletes the selected box or relation and what hangs on it, and afterwards nothing is selected, also if it only got marked as removed. There is no confirmation. Backspace does not delete.
* *What hangs on a box:* A class takes its relations along, with their association classes, and the notes attached to the class or to those relations. A relation takes its association class and the notes attached to it. An association class and a note take only themselves. An attribute takes the notes attached to it.
* *Without change tracking* everything which goes is removed.
* *With change tracking* the rule is the one of deleting a step in Specman: What a change set has added is removed at once, whichever change set it was. Whatever else goes is marked `change(removed, <change set>)` and stays visible, veiled. What is marked removed already stays as it is.
* The deletion is one operation and one undo step.
* Attributes are deleted by emptying their line, see <<Attributes>>.

## Editing Texts
All texts are edited in place, with a text field which lies over the text.

### Starting
* A double click on a text starts it. The first press of the double click selects the box under it, if there is one.
* The texts of the selected box can be changed: the name of a class (its name row), its stereotype (its row above the name), each tagged value (its row below the name), the text of a note, the lines of the attributes. The texts of a relation, its label and its multiplicities, can be changed without selecting anything. A text on a box which isn't selected can't be edited.
* Short texts have a larger area where a double click counts: the multiplicities and labels of relations reach 3 diagram units around the text.
* Only one text is edited at a time.

### The Field
* The field lies exactly where the text is, in its font, scaled with the zoom, aligned like the text (the class name is centered, the others start where the text starts). It has a blue border and is white. While changes are tracked, it has the pale color of the change set, as a reminder that the change will be marked.
* *Size:* A class name, a label and a multiplicity grow with the text as it is typed, at least 120, 80 and 40 pixels wide. The text of a note and the line of an attribute are wrapped at the width of their box while they are typed: the field has the width of the box and grows downwards (an attribute is wrapped only in the field, never in the diagram, see <<Width of a Class Box>>). The height always fits the text.
* The diagram is laid out anew after the commit only, not while typing.

### Ending
* *Return* commits. A line break in a text is made with Shift+Return or Ctrl+Return; where a text must not have one (multiplicities), a line break makes the text invalid. In the field of an attribute line there is no line break at all: Ctrl+Return and Shift+Return do nothing, and line breaks which are pasted become blanks, so an attribute never has more than one line in its source (the diagram still wraps a long one at the width of the box).
* *Esc* leaves the text as it was.
* *Leaving the field* (a click elsewhere, another window) commits, as Return does. The element which is changed is the one which was edited, also if the click selected another box.
* *Same text:* A text which is the same as before is no operation and no undo step.
* *Empty text:* A text which must exist (class name, note text) keeps its old content if the field is committed empty. A text which may be missing (label, multiplicity, attribute line) is removed by the empty text.
* *Whitespace:* Blanks at the ends are removed, tabs become blanks.
* *Invalid text:* A text which the element can't have, see below, is not committed. After Return the field stays open and gets a red border, which goes away with the next keystroke. After leaving the field the text is dropped.
* Every commit which changes something is one operation and one undo step.

### The Texts of the Element Kinds
[cols="1,3"]
|===
|Text |Rules

|Class name |Bold, centered. May have several lines. Mandatory.
|Stereotype |Plain, centered, one line, above the name. Typed without the angle brackets, which the field shows around the text and the diagram draws. May not contain `>`. Optional: empty removes it. See <<The Stereotype of a Class>>.
|Tagged value |Plain, centered, one line, one row for each, below the name. Typed as KEY=value or KEY without the braces, which the field shows around the text and the diagram draws. Optional: empty deletes it. See <<The Tagged Values of a Class>>.
|Note text |Plain, left aligned, wrapped at the width of the note. May have several lines. Mandatory.
|Relation label |Plain. May have several lines. Optional: empty removes it. Stands at the middle of the longest part of the line.
|Multiplicity |One at each end of an association, aggregation and composition. Free text, one line, optional. Anything is allowed, for example `1..<maximum capacity>`. In the source it is written without quotes if it is a number, a range like `0..1` or `1..*`, or `*`, otherwise in double quotes.
|Attribute line |See <<Attributes>>.
|===

### Texts Which a Relation Doesn't Have Yet
A selected relation shows where its missing texts would stand, as dashed rectangles in the color of the selection: one for the label, in the middle of the longest part of the line, and, for association, aggregation and composition, one for each of the multiplicities at the ends of the line. Inheritance and implementation have only the place for the label.

* A double click on a place opens the field, where the text would stand, in the same way as for a text which exists. The field starts as wide as the place, covering its dashed rectangle exactly sideways, is as high as the field for a text which exists, and grows with the text. The user types the text, Return gives the relation its text, as it is described for the texts above. Empty text or Esc creates nothing.
* While changes are tracked, the places are filled with the pale color of the change set, like the field is, as a reminder that the new text will be marked.
* A label or multiplicity which a change set has removed (the empty text with a mark) counts as missing and gets a place again. While changes are tracked, a new text has the mark without an old text, see <<Marks of Texts>>.
* The places belong to the selection, they are no part of the diagram: they are shown only while the relation is selected, can be clicked only then, and don't appear in the Aktogramm or in the PDF. A press or a double click on a place keeps the relation selected, like a press on a handle.
* The size of a place comes from a sample text (`DiagramStyle.LABEL_PLACEHOLDER` and `MULTIPLICITY_PLACEHOLDER`), laid out like a real text, so that the real text stands where its place was.
* The places lie beside the line, so a double click on the line itself still adds a waypoint.

A relation which has no label or multiplicity yet and isn't selected has no area to double click.

### The Stereotype of a Class
A class has at most one stereotype, shown as `<<Entity>>` in a row above its name. In the source it is a list entry like an info of an attribute: it can be added or removed as a whole, `change(added|removed, <change set>)`, and keeps its text when it is removed, and its text can be changed, `was(<change set>, <old text>)`. The order in the source is: text, text mark, ID, element mark. There is no empty stereotype `<<>>`.

* *Changing the text:* a double click on the row of the selected class starts the field. The user types the text without the angle brackets, which the field draws around it in the font of the text, so the field looks like the row. Return commits. The text is one line and can't contain `>`. Empty removes the stereotype. The ID of the stereotype stays when the text changes, and goes with the stereotype when it is removed.
* *A class without a stereotype:* shows nothing for it. The entry *Add stereotype* of the context menu of the class (see <<The Context Menu of a Class>>) puts a blank row above the name, with the field in it, so the user types the text right away. Before, a dashed place above the class did this; it was dropped because it was too tricky to hit and could not serve tagged values and attributes. The blank row is part of the picture, not of the diagram, like the blank line of a new attribute: the box of the class is one row taller while it is typed, nothing is reported to the host, and the row goes away if it stays empty, Esc is pressed, or the field is left.
* *While changes are tracked:* a new stereotype is marked as added (`<<Entity>> change(added, yellow)`), one which is removed keeps its text and is marked as removed, a changed one gets the text mark with the old text. A stereotype which the change set has added is gone without a trace if it is removed.
* *A removed stereotype* is drawn like a removed info: its text has the strong color behind it and a line through it. For the editor it counts as missing: its field is empty, typing the old text takes the removal back, typing another text changes the stereotype (text mark with the old text as backup). *Add stereotype* is offered for it and types into the struck row, which is there already. If another change set has removed it, a new text changes the text without a mark.
* *Display:* an added stereotype has the strong color behind its text, a changed one too (as a whole, the diff is not worth it for a word). The marks of a stereotype inside a class which a change set has added or removed are ignored.

### The Tagged Values of a Class
A class has any number of tagged values. Each one is drawn in a row of its own, below the name, in braces: `{TABLE=books}`, `{author=Jan}`, one below the other, centered like the name. In the source they stay one list in braces after the stereotype, `{TABLE=books, author=Jan}`. A tagged value without a value is written with an equals sign and nothing behind it, `{persistent=}`, because a bare `{persistent}` could not be told from the body of a class with one attribute. It is drawn as `{persistent}`. Like an info of an attribute, a tagged value is a list entry: it can be added or removed as a whole, `change(added|removed, <change set>)` behind its value, and keeps its text when it is removed. Its key and value can be changed, `was(<change set>, <old text>)` behind each of them. Tagged values have no ID of their own. Model-bound tags are a topic of Classman itself, see the open points.

* *Changing:* a double click on the row of a tagged value of the selected class starts the field, with the braces drawn around it like the angle brackets of a stereotype. The user types `KEY=value` or only `KEY`: the key is what stands before the first equals sign, written like a name without quotes (letters, digits, underscore, a hyphen or slash between them, not starting with a digit), the value is everything behind it, with blanks and equals signs, but no line break. The key is mandatory. The value is optional, but if there is an equals sign there must be a value: `eins` and `eins=zwei` are tagged values, `eins=` is not, and gets the red border at Return like any other text which isn't like that. Ctrl+Return and Shift+Return make no line break, pasted line breaks become blanks, as for attributes. Return commits.
* *Each tagged value on its own:* only the row which was double clicked changes. The empty text deletes the tagged value. Typing only the key takes the value away, which is marked like any changed value while changes are tracked (the old value is the backup). A removed value can't be shown, so the change is visible only in the source, as a small open point.
* *Adding:* the entry *Add tagged value* of the context menu puts a blank row after the last tagged value and starts the field in it, empty. The blank row is part of the picture, not of the diagram (nothing is reported to the host, no undo step), and goes away if it stays empty, Esc is pressed or the field is left. There is no going on with the next one after Return, as there is for attributes: the entry is chosen again.
* *Deleting:* the empty text. Without change tracking the tagged value is gone. While changes are tracked, one which the change set has added is gone without a trace, any other is marked removed and keeps its text. A removed tagged value has no row to change any more, it can be taken back with undo or by rejecting the change set.
* *While changes are tracked:* a new tagged value is marked as added, a changed key or value gets the text mark with the old text, so only what changed is marked, not the whole row. In a class which a change set has added or removed, and in a tagged value of that kind, nothing is marked, the marks would be ignored.
* *Display:* an added tagged value has the strong color behind its row, a removed one the color and a line through it, a changed key or value the color behind just that part. With a width of its own the class cuts every row off on its own, see <<Width of a Class Box>>.
* *Accepting and rejecting* a change set: an added tagged value stays or goes, a removed one goes or stays, the text marks keep the new or bring back the old key and value, like for every text.

## The Context Menu of a Class
The right mouse button on a class selects it, like a press, and opens a menu with the parts which the class can get. A note has a menu too, with only the automatic width, see <<Width of a Note>>. Parts of a class are not created by buttons or by dashed places on the diagram, because a place above or between the parts is hard to hit and the number of places grows with every kind of part. The menu is the one way to create them; editing what exists stays a double click.

* *Add stereotype:* see <<The Stereotype of a Class>>. Offered (can be chosen) only if the class has no stereotype, or one which a change set has removed.
* *Add attribute:* puts a blank line at the end of the attributes and starts typing into it, see <<Adding Attributes>>. Return in that line goes on with the next one.
* *Automatic width:* see <<Width of a Class Box>>. A check item, separated from the entries which add parts.
* *Add tagged value:* puts a blank row after the last tagged value and starts typing into it, see <<The Tagged Values of a Class>>. A class which a change set has removed offers nothing.
* An entry which doesn't fit can't be chosen, it is not hidden, so the menu looks the same on every class. A class which a change set has removed offers nothing.
* A text which is being typed is finished first when the menu is opened: the right button takes the focus to the canvas.
* The menu belongs to classes of the diagram. Association classes, notes and relations have none yet, a right click on them only selects them. While the tool for relations is armed, there is no menu.
* The texts of the entries are in the editor's own bundle (`menu.class.add.*`).

## Attributes
An attribute is edited as a whole line, in the form in which the diagram shows it: `+name : type [info, info]`. The user types it as text, the editor splits it into its parts when the line is committed. Reason: it is one gesture for everything, including adding a type or an info which the attribute doesn't have yet, and it is how UML tools are used. The alternative, a field for each part, needs many small click areas in one short line, and has none for parts which are missing.

### The Line
* *Visibility:* an optional first sign: `+` public, `-` private, `#` protected, `~` package. Blanks after it are allowed.
* *Name:* what stands before the first colon. It may contain blanks and needs no quotes. It is mandatory.
* *Type:* what stands after the first colon, up to the infos. Optional; a colon with nothing after it is no type. A diagram shows the colon only if there is a type: with no type, or with a type which a change set has removed, there is no colon either.
* *Infos:* items between ` [` and the closing `]`, separated by commas. Optional. An item which contains a comma, a quote, a closing bracket or a backslash is shown and typed in double quotes: `["a, b", "say \"hi\""]`. Empty items are dropped.
* *Not possible:* a name or type which contains a colon, or a name or type which contains ` [`: they would be taken for the next part.
* *Invalid lines:* no name; brackets which aren't closed; a line break (which the field can't produce, only a hand-written source can); the line `...` (the marker for attributes which the diagram doesn't show; it can't be edited and can't be typed).
* The field shows the attribute as the diagram does, so a line which is committed unchanged is no operation.

### Changing an Attribute
* Double click on a line of the selected class; the field covers all rows of the line if it wraps in the field.
* The parts which differ are changed, the others stay. Without change tracking nothing is marked.
* *Infos:* The infos which are the same in the old and the new line stay, in their order. In the gaps between them, the old infos are changed into the new ones one by one, whatever is left over is removed, or added after the last info before it. This makes a changed info one change and not a removal and an addition.
* *Change tracking:* The name and the type get `was(<change set>, <old text>)` where they differ. An info is a list entry, like an attribute in a class, so it takes element marks: an info which is added is marked `change(added, ...)`, one which is removed is marked `change(removed, ...)` and keeps its text. An info whose text is changed gets a text mark with its old text. An info which a change set has added is simply gone if it is removed, whichever change set it was. An info which the change set has removed and which is typed again is not removed any more: it is found by its text and stays where it was, also if it was typed at another place of the line. Another text typed in its place is a new info, and the removed one stays struck through next to it. A removed type stays as the empty text with its mark and is not shown, see <<Removed Parts of a Line>>. Setting a part back to its old text takes the mark away.
* *Visibility sign:* has a mark like the other parts: `+ was(yellow, "-") name`. A sign which was there can't be removed while changes are tracked, because with no sign left there is nothing to carry the mark; the line is invalid then (red border). A sign which the change set added itself can be removed again, and in an added or removed attribute or class all this doesn't matter, since marks inside them are not shown. It is assumed that a diagram works either with visibility signs or without them, and doesn't switch in the middle of a change set; so the restriction is expected to be rarely met. Whether it is a nuisance in practice has to be watched, see <<Open Points>>.
* In a class which a change set has added or removed, and in an attribute of that kind, attributes are changed without marks.

### Deleting an Attribute
The empty text deletes the attribute: the user selects all, deletes, presses Return. Without change tracking the attribute and the notes attached to it are removed. With it, the rule of <<Deleting>> applies: an attribute which a change set has added is removed at once, otherwise it is marked `change(removed, <change set>)`, and so are the notes attached to it.

### Adding Attributes
* The entry *Add attribute* of the context menu of the class puts a blank line at the end of the attributes and starts typing into it.
* A class without attributes shows one blank line. Double clicking it starts a new attribute, too.
* *Return in the last line of a class* commits it and opens a blank line below for the next attribute, until a line is committed empty. *Esc*, or leaving the field, ends the sequence; a blank line which stays empty is not an attribute. Return in any other line only commits.
* While the blank line is typed, the box of the class is one line taller. The blank line is part of the picture but not of the diagram: it is not reported to the host, and it goes away again if it is dropped.
* The new attribute is marked `change(added, <change set>)` while changes are tracked, in an added or removed class it carries no mark.
* A new attribute gets no ID. IDs are needed only for attaching notes.
* Every committed line is one operation and one undo step.

### Not Built
Moving an attribute within its class (by dragging, or with Alt+Up and Alt+Down), editing the `...` marker, selecting an attribute.

## Change Tracking in the Editor
If the host says that changes are tracked, the editor writes the marks: the user never writes them by hand. Accepting, rejecting and merging change sets is done by the host on the source, see `ChangeResolver_V001`, outside of the editor.

### Why a Change Mode
Software is developed in increments, sprint by sprint, and so are its specifications and models. A class diagram is not drawn once, it grows and changes with every sprint, and the people who work with it need to see *what is new in this sprint* against what existed before, and to decide about it: take it over, or throw it away. A diagram which only shows the current state can't say that. A history of file versions can, but only as a difference between two files, without the unit which matters in the work: the sprint, or a task, which is accepted or rejected as a whole.

Specman has this for Aktogramme: changes are collected in change sets, shown in the color of the change set, and accepted or rejected as a whole. Classman gives class diagrams the same. This is a core feature of the editor and not an extra, and it shapes the rules:

* *The change set is the unit.* The user doesn't change a diagram and a history afterwards: they work inside a change set, and everything they do is part of it. Accepting or rejecting a change set decides about all of its changes in all diagrams at once.
* *The diagram shows the new state and marks the difference.* The people who read the diagram work with the new state, so that is what is shown. The marks say where something is new, changed or gone, in the color of the change set. The old text is not shown in the diagram, so that hand-made layouts keep their shape.
* *The old state is kept, in the source.* A rejected change must be able to bring back exactly what was there. The marks therefore carry the old text, and removed things stay in the source until the change is accepted.
* *The difference stays readable in the source.* The marks are plain text, in a fixed form, next to what they mark. People and programs, such as agents which are asked to review or write changes, can read and write them without a tool.
* *The same rules for everything.* A class, an attribute, an entry in a list, a relation, a text: each can be added, removed, or (for texts) changed, and each is marked in the same way, so that the user doesn't have to learn a rule per element kind.
* *Marking is the editor's job.* The user edits as usual. If the host says that changes are tracked, the editor writes the marks; the user never writes one by hand.
* *Not everything is a change.* Moving a box changes the picture, not the model. Moves are never marked.

### The Concept of Change Marks
A diagram is changed by change sets, as the steps of an Aktogramm are, and the marks in the source say which change set did what. The marks have a fixed form so that the people and the programs who read the source can rely on it:

* *Two kinds of marks.* An *element mark*, `change(added|removed, <change set>)`, says that a whole class, attribute, info of an attribute, relation, association class or note was added or removed. A *text mark*, `was(<change set>, <old text>)`, says that a text of an element was changed. The element is the same, the text is new.
* *The text mark stands behind the text it belongs to.* The current text stays readable and searchable in the source, which matters for agents, and the style is the one of the element marks. The old text is the backup in the mark.
* *The text shows the new state only.* The old text is not shown in the diagram, as Specman does it with its struck-through text, because the boxes of a diagram are laid out by hand and must not grow or shrink by a change. The diagram shows *that and where* something changed, the old text is in the source.
* *The change set is the unit.* A change set is accepted or rejected as a whole, for the whole diagram. The marks of other change sets stay as they are.
* *Accepting and rejecting* (done by the host, outside of the editor):
** An element which was *added*: accepting keeps it and drops the mark, rejecting removes it.
** An element which was *removed*: accepting removes it, rejecting keeps it and drops the mark.
** A text which was *changed*: accepting keeps the new text and drops the mark, rejecting brings back the old text. A text which didn't exist before is gone after rejecting, a removed optional text is gone after accepting.
** What hangs on an element goes with it, whatever its own marks say: a class takes its relations, association classes and the notes attached to it or to them; an attribute or a relation takes the notes attached to it.
* *Renaming a change set* (merging two into one) renames its marks. This is also done by the host.
* *Moves are never marked.* A box which is moved is moved, and that is all.
* *The host decides whether changes are tracked.* Without tracking, the editor writes no marks and changes the diagram directly.

How the editor writes the marks for each operation is described with the operation. The rules for texts are collected below.

### Marks of Elements
`change(added, <change set>)` and `change(removed, <change set>)` follow the ID of a class, attribute, relation, association class or note, and the text of an info of an attribute (`[a, b change(removed, yellow)]`), of a stereotype (`<<Entity>> change(removed, yellow)`) or of a tagged value (`{a=1 change(removed, yellow), b=2}`). Moving an element is never marked. Rules for deleting: <<Deleting>>.

### Marks of Texts
`was(<change set>, <old text>)` follows the text which a change set has changed, which always stands for the new state. Every text of the diagram can carry one: the diagram name, class name, stereotype, key and value of a tagged value, the visibility sign, name and type of an attribute, an info, a multiplicity, a relation label, a note text.

* The old text is the text from before the change set started, however often it is changed. Setting the text back to it takes the mark away.
* A text which didn't exist before has a mark without old text. An empty old text says it was empty.
* An optional text which is removed stays as the empty text with the mark: `"" was(yellow, "old label")`. This holds for labels, multiplicities and types. It is not shown, there is nothing left to show. The exceptions are the visibility sign, which can't be removed, and the infos of an attribute and the stereotype of a class, which are list entries and get element marks. A source which writes a removed info as `"" was(...)` is still read, and shown like a removed type.
* If another change set has changed the text before, the change set which changes it now takes the change over: its old text is the text from before this change.
* The marks of texts inside an element which a change set has added or removed are ignored in the display. So these texts are changed without a mark.
* If a text which a change set has added is removed again, it is gone without a trace.

### What the User Sees When an Input is Completed
This section collects, for every input which the user completes, what is colored afterwards and in what color. It repeats rules which are given with the operations, so that the use cases can be derived from one place. The color is always the color of the change set which tracks the changes, and what is colored is always the new state, the old text is only in the source.

*Completing an input:*

* *Return* completes it. *Leaving the field* (a click elsewhere, another window) completes it in the same way. The result is drawn at once.
* *Esc* completes nothing: nothing changes and nothing is colored.
* *The same text as before* changes nothing and colors nothing.
* *A text which isn't valid* completes nothing. After Return the field stays open with a red border, and nothing is colored. After leaving the field the text is dropped.
* *The empty text* completes nothing for a mandatory text (class name, note text): the old text stays. For an optional text (label, multiplicity, stereotype, tagged value, attribute line) it removes the text or the element. A new class, stereotype, tagged value or attribute which is completed empty is not created and nothing is colored.
* *While typing,* nothing of the diagram is colored yet. The field has the pale color of the change set if changes are tracked, white otherwise. A new part (class, stereotype row, tagged value row, attribute line) is already shown as a blank place, which is not part of the diagram yet.

*What happens to the colors:* Three circumstances decide.

* *Not tracked:* the host does not track changes. Nothing is colored, in no case.
* *Tracked, element not marked:* changes are tracked, and the element which the input belongs to (the class, the note, the relation, the attribute) has no mark of its own.
* *Tracked, element added or removed:* changes are tracked, but the element has been added or removed by a change set already. The frame, band or row of that element says that everything in it is new or gone, so what is typed into it is not colored on its own, whichever change set it was. This is the case for everything the user adds to a class which was created in the same change set.

* *Drawing an association* (releasing the mouse on a class): not tracked: none. Tracked: a band of 9 units in the strong color below the line. It is the same with the other kinds of relations which will come.
* *Deleting with the Delete key:* not tracked: gone. Tracked: a class or note which a change set has added is gone without a trace, any other gets the frame of the change set, is veiled, and its name has the strong color behind it and a line through it. A relation which is not added gets the band, a grey line, a cross and a struck label. What hangs on it is marked in the same way.
* *Moving and changing the width* of a class are never colored, in no case.

If a change set changes a text which another change set has changed before, the color becomes the color of the change set which changed it last, and it takes over the old text of the other one as its own old text. *Small diagrams:* when the diagram is shown small, frames, bands and the strong color behind texts keep a minimum size on the screen, so that none of this disappears, see <<Marks in Small Diagrams>>.

## Display of Changes
These rules decide how a diagram with marks looks, also in the Aktogramm and in the PDF.

* *Colors:* every change set has a strong color and a pale one (60 % white). The host maps the name of a change set to the colors.
* *Added or removed class or note:* a frame in the strong color around the box, 12 units wide, of which 6 show outside the border. Removed ones are also veiled (half white), their texts grey, their name has the strong color behind it and a line through it. The marks of the texts inside are not shown.
* *Added or removed attribute:* the row has the pale color, its text the strong color behind it; removed attributes have a line through the text.
* *Added or removed info of an attribute:* the same for the info only: its text has the strong color behind it, and a removed info keeps its text and has a line through it. The line keeps its length: a removed info was there before, so nothing grows.
* *Added or removed stereotype:* the same as for an info: the text has the strong color behind it, a removed one keeps its text and has a line through it.
* *Added or removed relation:* a band of 9 units in the strong color below the line. A removed relation has a grey line, a cross at a quarter of its longest part and a label which has the strong color behind it and a line through it.
* *Changed text:* a background in the strong color behind the part of the text which changed, see below. The old text is not shown, so the box doesn't change its size, which matters in hand-made layouts.
* *Not marked:* moves, and the visibility sign of an attribute of an added or removed element.

### Which Part of a Changed Text is Marked
For a long text, marking all of it is too much if only one character changed. The part is found by comparing the old text with the new one (diff):

* New text is marked.
* Where text is gone, the nearest characters before and after the gap which aren't blank are marked, with the blanks between them. At the start of the text only the first character after the gap is marked, at the end only the last one before it.
* Text which is replaced by other text is shown by the new text alone.
* Marks which are at most 3 characters apart become one.
* If there are more than 8 separate marks, the two which are closest together become one, until 8 are left.
* The whole text is marked if there is no old text, if it is shorter than 12 characters, or if the marks would cover more than 80 % of it.

The numbers are tuning knobs in `DiagramStyle` (`DIFF_MIN_TEXT_LENGTH`, `DIFF_MERGE_GAP`, `DIFF_MAX_RUNS`, `DIFF_WHOLE_SHARE`). Marks for new text and for gaps look the same, the reader sees that something changed here, not what.

### Removed Parts of a Line
A type which a change set has removed is the empty text with a mark. It is not shown, and neither is its colon. The place where it was is marked by the same rule as a gap in a changed text: the last character before it, the end of the name. The same rule applies to an info which a source writes as the empty text with a mark.

An info which is removed with the element mark, which is what the editor writes, keeps its text and is shown struck through, see <<Display of Changes>>. This was first done differently, with the empty text and the neighbors of the gap marked, until the user pointed out that an info is a list entry, as an attribute is, and the list should show what was removed from it. A removed label or multiplicity has no line it could be struck through in and is not marked at all so far, see <<Open Points>>.

### Marks in Small Diagrams
When the diagram is shown small, marks must not disappear. Strokes of frames and bands keep a width of at least 6 pixels on the screen, strong highlights of texts a height and width of at least 8 pixels, whatever the zoom is (`DiagramStyle.MIN_VISIBLE_STROKE` and `MIN_VISIBLE_HIGHLIGHT`). A highlight which is made larger this way may reach over its neighbors.

## Undo and Redo
* The history is Specman's. After each operation the editor reports the whole new source, and Specman makes one undo step of it. Reason: this is simple, and a growing grammar needs no change of the undo.
* The editor counts the steps it has reported itself. Ctrl+Z undoes only those, so never reaches back to what happened before the window was opened; Ctrl+Y and Ctrl+Shift+Z redo them. After undo or redo the editor reads the source anew: nothing is selected.
* A new operation clears the steps which could be redone.
* Operations which change nothing, like committing a text unchanged, are no steps.
* A move is reported when the mouse is released, one step for the whole drag.
* The keys belong to the text field while a text is typed.

## Consequences for the Format
The grammar is `ClassDiagram_V001.g4`, its header describes every rule. What the editor needed, and what was decided on the way:

* Relations and the anchors of their routes refer to classes by their IDs, class names are free text. A class needs an ID to take part in a relation.
* Multiplicities are free text, written without quotes only if they are a number, a range or `*`.
* All strings are in double quotes, which is why a source can be embedded into Specman's model without escaping. Backticks are not allowed.
* The visibility sign of an attribute can carry a text change mark.
* The infos of an attribute are list entries: they take the element marks `change(added|removed, ...)`, and keep their text as a removed info. Their text mark `was(...)` is for changing the text.
* Elements created by the editor get an ID (classes) and a position `at(x, y)`. Attributes get an ID only if a note is attached.
* Planned: new keywords `interface` and `enum`. An interface has no body. An enum has values written like attributes without a type. The layouter and the change mark logic have to handle the new kinds.

## Tests
* Tool state and every operation on the model are plain logic and are tested without a window; the field and its keys are tested headless on the event dispatch thread.
* The look of the window and the feel of the mouse operations are checked by hand.
* The dependency rule between `classman.*` and `specman.*` is tested.

Everything which the user adds to a class which is new in the same change set is not colored on its own, only the frame of the class says that it is new (see <<What the User Sees When an Input is Completed>>). The other way round would mean that the new class gets no frame as soon as it has parts, or that its parts are colored too and the frame is no longer needed to read the diagram.

. Model-bound mode of Classman (only stereotypes and tags defined in the model can be chosen) is a separate topic and not part of this concept.
