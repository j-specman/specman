## Windows installer
Besides the plain executable JAR, Specman can be packaged as a Windows Setup EXE with a bundled Java runtime, so end users don't need a JRE installed. The build is two steps, both driven by Maven: `jpackage` creates the app image (`Specman.exe`, `specman-cli.exe` and the bundled runtime in `target/jpackage-app-image/Specman/`), then https://jrsoftware.org/isinfo.php[Inno Setup] 6 packs that directory into the installer (`src/main/inno/specman.iss`). Building requires JDK 17+ (for `jpackage`) and Inno Setup 6, e.g. via winget:

[source,shell]
----
winget install JRSoftware.InnoSetup
----

`ISCC.exe` (the Inno command-line compiler, in the Inno Setup installation directory, e.g. `C:\Program Files (x86)\Inno Setup 6` or `%LOCALAPPDATA%\Programs\Inno Setup 6`) must be on the `PATH`, or its location is passed explicitly:

[source,shell]
----
mvn -P windows-installer clean package
mvn -P windows-installer clean package "-Dspecman.inno.iscc=%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe"
----

The resulting `specman-<version>-windows-setup.exe` is written directly to `target/`, next to the portable zip from `mvn -P release-bundle package` (if built).

### What the installer does
* *Install mode.* At startup the installer asks whether to install "for all users" (recommended, preselected, needs admin rights) or "only for me" (no admin rights). System-wide installs go to `%ProgramFiles%\Specman` and register the `.nsd` association and the `PATH` entry machine-wide (HKLM); per-user installs go to `%LOCALAPPDATA%\Specman` and register both for the current user only (HKCU). Upgrades and uninstalls reuse the mode of the existing installation. For unattended installs: `/VERYSILENT /ALLUSERS` or `/VERYSILENT /CURRENTUSER` (`/DIR="<path>"` overrides the target directory).
* *Shortcuts and tools.* A Start menu entry, an optional desktop shortcut (task in the wizard) and the `specman-cli` console launcher for the link:src/main/java/specman/cli/SpecmanCLI.java[command-line operations].
* *File association.* `.nsd` files are associated with Specman (including the icon).
* *Grammar and reference model.* `SpecmanModel_V002.g4` and `specman-reference-v<major.minor>-*.nsd` (for AI-assisted spec authoring) are installed directly into the installation directory, at the same relative position as in the portable zip.
* *`specman` on the `PATH`.* A small `specman.cmd` forwarder to `specman-cli.exe`, installed into its own `bin` subdirectory so it can't clash with `Specman.exe` — Windows filenames are case-insensitive. Open a *new* terminal after installing (PATH changes only apply to newly started processes) and run e.g. `specman --sanitize <file>`.
* *Updates.* The installer's `AppId` (`specman.installer.appId` in `pom.xml`) is a fixed GUID and must not change. Installing a newer version over an existing one upgrades it in place; bump `<version>` in `pom.xml` between releases (the installer file name, the version shown in "Apps & Features" and the bundled launcher version all follow `<version>` automatically; it must be purely numeric, `-SNAPSHOT` is rejected by `jpackage`, and a `specman-reference-v<major.minor>-*.nsd` for the new `major.minor` must exist). Before copying, the installer clears `app\` and `runtime\` of the existing installation and the old reference model/grammar files (`[InstallDelete]`), so the previous version's jar and reference model (their names contain the version) don't pile up. The install mode is taken over from the existing installation and not asked again; the directory page is always shown, prefilled with the existing directory (choosing a different directory leaves the old files behind, uninstall first if you want to move).
* *Uninstall.* Via "Apps & Features" or `unins000.exe` in the install directory; removes the files, the file association and the `PATH` entry. If Specman is still running, the uninstaller asks to close it first (Retry/Cancel) instead of silently skipping the locked files; with `/VERYSILENT /SUPPRESSMSGBOXES` it aborts with exit code 1 and changes nothing. Inno only removes directories it created itself: if the install directory already existed (e.g. leftovers of an earlier, aborted uninstall), empty folders can remain after uninstalling — delete the old directory before installing.

### Testing the installer
Uninstall every previous Specman installation first (see <<Migrating from an older installation>>), then check:

. *Install system-wide:* run the EXE, keep "for all users" (UAC prompt), finish the wizard. Specman starts from the Start menu entry and from the final "Launch Specman" checkbox. The install directory contains `SpecmanModel_V002.g4` and the `specman-reference-v*.nsd` directly (as in the portable zip), not below `app\`.
. *File association:* double-click a `.nsd` file (e.g. `doc/anagramms.nsd`); it opens in Specman and shows the Specman icon in Explorer.
. *Command line:* in a *new* terminal, `specman --sanitize <file>` works; `where specman` points to `<install dir>\bin\specman.cmd`.
. *Upgrade:* bump `<version>`, build again and run the new installer over the existing installation; no second entry in "Apps & Features", the old version is replaced, the `PATH` entry exists only once.
. *Uninstall:* via "Apps & Features"; the install directory, Start menu entry, `.nsd` association and `PATH` entry are gone.
. *Per-user mode:* repeat 1–5 with "only for me" (no UAC prompt, install directory `%LOCALAPPDATA%\Specman`).

### Migrating from an older installation
* *Former MSI installer.* An installation made with the previous MSI is not replaced by the Setup EXE (different installer technology). Uninstall it via "Apps & Features" first, otherwise both register the `.nsd` association and a `PATH` entry.
* *Manual `SPECMAN_HOME` + `specman.bat` setup.* The `.nsd` file association is not taken over automatically. Windows remembers an explicit prior choice (`HKCU\...\FileExts\.nsd\UserChoice`) and, in setups where the association was registered directly rather than picked via "Open with", also a plain `HKCU\Software\Classes\.nsd` entry pointing at the old ProgId/batch file — neither is overwritten by the installer. After installing, reset both if `.nsd` files still open the old way:
+
[source,powershell]
----
Remove-Item -Path "HKCU:\Software\Microsoft\Windows\CurrentVersion\Explorer\FileExts\.nsd" -Recurse -Force -ErrorAction SilentlyContinue
Remove-Item -Path "HKCU:\Software\Classes\.nsd" -Force -ErrorAction SilentlyContinue
----
+
(the second command's target ProgId name depends on how the old install registered itself, e.g. `nsd_auto_file`; inspect `HKCU:\Software\Classes\.nsd` first to find it, and remove that ProgId key too). Then pick the new `Specman.exe` once via "Open with" → "Always use this app".

### Known limitations
* *The installer and `Specman.exe`/`specman-cli.exe` are not code-signed.* On first run, Windows SmartScreen (and/or Defender) may block the unsigned executable ("Windows hat den PC geschützt"). For local testing: `Unblock-File <path-to-exe>`, or click "Weitere Informationen" → "Trotzdem ausführen" in the SmartScreen dialog, or add a Defender exclusion for the install directory. For real-world distribution the EXE should be signed with an Authenticode certificate (Inno's `SignTool` directive, plus `signtool sign /fd sha256 /tr <timestamp-url> ...` for the launchers in the app image) so end users don't hit this at all.
* *Build machine antivirus/EDR can block the build.* Some products (observed with Windows Defender and the former WiX-based build) deny read access to `klist.exe`, a Kerberos tool bundled in the `java.security.jgss` module that gets pulled into the runtime image transitively (likely via asciidoctorj/JRuby or iText). Inno reads every file of the app image when compressing, so a similar block is possible. Workaround: add a temporary exclusion for the build directory before building, e.g. from an elevated PowerShell: `Add-MpPreference -ExclusionPath "$env:LOCALAPPDATA\Temp"`. Excluding the `java.security.jgss` module itself (Specman doesn't use Kerberos/SSO) would be a cleaner fix but hasn't been implemented/verified yet.
* *The bundled runtime is not module-trimmed.* jpackage's automatic `jdeps`-based module detection is used as-is (plus `--strip-debug`/`--no-header-files`/`--no-man-pages`), so the installer is relatively large (~80 MB). A curated `--add-modules` list could shrink this but needs testing against every feature (PDF export, Asciidoc export, etc.) to avoid removing something actually required.
* *No MSI.* The Setup EXE is not suitable for MSI-based software distribution (GPO, Intune).
