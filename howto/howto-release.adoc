= How-to: Release erstellen und auf GitHub veröffentlichen
:toc:
:sectnums:

== Zweck und Geltungsbereich

Dieses How-to beschreibt den gesamten Ablauf eines Specman-Releases:

* das Bauen der Release-Artefakte (Windows-Installer und portables ZIP),
* das Prüfen der Artefakte und
* das manuelle Anlegen des GitHub-Releases im Repository `j-specman/specman` und
* das Aktualisieren der Website im Repository `j-specman/j-specman.github.io` (siehe <<website,Website aktualisieren>>).

Der Ablauf gilt für:

* ein neues Release auf dem aktuellen Hauptbranch `master` und
* die nachträgliche Veröffentlichung einer älteren Version (siehe <<aeltere-releases,Ältere GitHub-Releases nachträglich veröffentlichen>>).

Der Release wird auf einem Windows-Rechner gebaut, weil der Installer Inno Setup benötigt.

== Voraussetzungen für den Build

* JDK 21 oder höher, auch von Maven verwendet (`jpackage` gehört zum JDK).
* Maven.
* *Docker*, laufend. Das Manual-PDF wird von `asciidoctor-pdf` aus dem Image `asciidoctor/docker-asciidoctor` erzeugt, das beim ersten Mal automatisch geladen wird. Dieser Build-Schritt läuft in beiden Release-Profilen, siehe Execution `manual-pdf` in der `pom.xml`.
* Inno Setup 6 mit `ISCC.exe`. Installation und das Problem mit Virenscannern auf dem Build-Rechner sind in link:howto-windows-installer.adoc[How-to: Specman Windows Installer] beschrieben.
* Schreibberechtigung für das Repository `j-specman/specman` und Zugriff auf dessen Releases-Bereich.

== Version vorbereiten

. Den vorgesehenen Release-Branch auschecken, aktuell, mit allen Änderungen, die ins Release sollen, committet. Bei einem Major Release ist das der Branch `master`, bei einem Minor Release der Branch `<major>.<minor>.x`.

. `<version>` in der `pom.xml` auf die Release-Version setzen, zum Beispiel `1.4.0`. Die Version muss rein numerisch sein, `-SNAPSHOT` lehnt `jpackage` ab.

. Prüfen, dass im Projekt-Root ein Referenzmodell `specman-reference-v<major.minor>-*.nsd` für die neue `major.minor` existiert (zum Beispiel `specman-reference-v1.4-model-v2.nsd` für 1.4.0). Ohne dieses Modell schlagen beide Release-Builds fehl. Es muss zur Grammatik `SpecmanModel_V002.g4` dieser Version passen.

. Das Manual `doc/specman-manual.adoc` prüfen: Der Titel enthält die Version (`# Specman 1.4 Manual`), und die neuen Features des Releases sind dokumentiert. Außerdem die Screenshots prüfen, ob sie noch aktuell genug sind in Hinblick auf Gestaltung in Inhalt der Menüs. Sie müssen nicht top aktuell sein, sollten aber auch nicht irreführend alt sein.

[#release-notes]
=== Release Notes schreiben

Die Release Notes liegen in `releasenotes/release-notes-<major.minor.patch>.md`. Sie werden später in das GitHub-Release und in die Release-Historie der Specman Web Site eingefügt.

*Inhalt:* die wichtigsten Änderungen, bekannte Einschränkungen, Upgrade-Hinweise und die Liste der enthaltenen Dateien. In der Regel stehen im Kopfbereich von `todos-specman.txt` in Stichworten die wichtigsten Änderungen, die in den Release Notes ausgeführt werden. Man kann sich daraus einen ersten Entwurf der Release Notes KI-generieren lassen.

*Format:*

* Github verlangt zwingend Markdown als Format.
* Die Überschrift lautet `## Specman <major.minor.patch>`, zum Beispiel `## Specman 1.4.0`.
* Direkt darunter steht eine Zeile mit dem Veröffentlichungsdatum im ISO-Format, zum Beispiel `Released: 2026-11-07`. Die Generierung der Release-Historie auf der Website liest das Datum aus dieser Zeile und zeigt es hinter der Version an. Fehlt die Zeile oder ist das Datum ungültig, schlägt der Website-Build fehl.

Der Anfang einer Datei sieht also so aus:

[source,markdown]
----
## Specman 1.4.0
Released: 2026-11-07

...
----

== Testsuite ausführen

Vor dem Bauen einmal die gesamte Testsuite ausführen, damit man es hinterher beim Release-Build nicht doppelt tun muss:

[source,shell]
----
mvn clean test
----

Bei einem fehlgeschlagenen Test nicht weitermachen.

== Artefakte bauen

Beide Release-Builds überspringen die Tests (sie sind ja gerade gelaufen) und brauchen zwei getrennte Maven-Aufrufe. Die Reihenfolge ist wichtig: Der erste Aufruf räumt `target/` auf, der zweite darf das nicht tun, sonst würde er den Installer wieder löschen.

[source,shell]
----
mvn -P windows-installer clean package -DskipTests "-Dspecman.inno.iscc=%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe"
mvn -P release-bundle package -DskipTests
----

Die Property `specman.inno.iscc` kann entfallen, wenn `ISCC.exe` im `PATH` liegt. Details dazu siehe link:howto-windows-installer.adoc[How-to: Specman Windows Installer].

Beide Aufrufe rendern das Manual (`target/specman-manual.pdf`) und erzeugen `readme.adoc` aus dem Manual neu. Hat sich `readme.adoc` geändert, wird die Datei committet.

Die Ergebnisse liegen in `target/`:

[cols="1,2"]
|===
|`specman-<version>-windows-setup.exe` |Windows-Installer
|`specman-<version>-portable.zip` |Portables Bundle für Windows und Linux
|`specman-installation/<major.minor>/` |Dieselben Dateien wie im ZIP, im Layout der Fileserver-Kopie
|===

== Artefakte prüfen

. *ZIP-Inhalt:* Im Root des ZIP liegen `specman.bat`, `specman-cli.bat`, `specman.sh`, das Jar mit Abhängigkeiten, `SpecmanModel_V002.g4`, `specman-reference-v<major.minor>-*.nsd`, `specman-manual.pdf`, `specman-readme.html` und `specman.png`.
. *Manual:* `specman-manual.pdf` öffnen und Titel, Version, Bilder und die Icons in den Überschriften prüfen.
. *Portables Bundle:* In ein neues Verzeichnis entpacken, `specman.bat` starten und das Referenzmodell öffnen. Auf einer Kopie davon `specman-cli.bat --sanitize <Datei>` ausführen - dabei muss "OK" herauskommen.
. *Installer:* Die Checkliste im Abschnitt "Testing the installer" aus link:howto-windows-installer.adoc[How-to: Specman Windows Installer] durchgehen, mindestens Installation für alle Benutzer, Dateizuordnung, Kommandozeile und Upgrade über die Vorversion. Im Installationsverzeichnis muss `specman-manual.pdf` neben Grammatik und Referenzmodell liegen.

== Release-Commit pushen

Versionsänderung und `readme.adoc` committen und pushen. Dieser Commit ist der Release-Commit, auf den der Tag zeigen soll.

Handelt es sich um einen Major-Release aus `master`, jetzt zunächst den Release-Branch `<major>.<minor>.x` anlegen und pushen.

== GitHub-Release vorbereiten

Vor dem Öffnen des Release-Dialogs müssen folgende Informationen und Dateien vorliegen:

. Schreibberechtigung für das Repository `j-specman/specman` und Zugriff auf dessen Releases-Bereich.
. Die eindeutige Versionsnummer, zum Beispiel `1.3.2`.
. Der passende Commit im Repository.
** Für ein neues Release ist das der geprüfte Release-Commit auf `master`.
** Für ein älteres Release muss der historische Release-Commit anhand der Git-Historie eindeutig bestimmt worden sein.
. Der Tagname im Format `v<version>`, zum Beispiel `v1.3.2`.
** Existiert der Tag bereits, muss er auf den passenden Commit zeigen.
** Existiert er noch nicht, muss ein passender Target-Branch vorhanden sein, dessen aktueller Stand dem Release-Commit entspricht. GitHub legt den neuen Tag beim Erstellen des Releases auf diesem Target an.
. Die geprüften Release-Artefakte aus `target/`. Dateiname und enthaltene Version müssen zum Release passen.
. Fertige Release Notes mit den wichtigsten Änderungen, bekannten Einschränkungen, Upgrade-Hinweisen und einer Liste der enthaltenen Dateien.

Vor dem Veröffentlichen muss außerdem feststehen, ob es sich um ein reguläres Release oder ausdrücklich um eine Vorabversion handelt.

== GitHub-Release anlegen

. Das Repository `j-specman/specman` auf GitHub öffnen.
. **Releases** öffnen.
. **Draft a new release** auswählen.
. Unter **Choose a tag** den vorhandenen passenden Tag auswählen oder einen neuen Tagnamen im Format `v<version>` eingeben und **Create new tag** auswählen.
. Wenn ein neuer Tag angelegt wird, als Ziel (**Target**) den Branch auswählen, dessen aktueller Stand dem zuvor bestimmten Release-Commit entspricht. GitHub bietet im Release-Dialog die Auswahl eines Branches an, nicht die freie Auswahl eines beliebigen Commits.
. Als Titel des Releases `Specman <version>` eintragen, zum Beispiel `Specman 1.3.2`.
. Die vorbereiteten Release Notes in das Beschreibungsfeld einfügen.
. Die vorbereiteten Artefakte (Installer und ZIP) in den Bereich für Release Assets ziehen oder über die Dateiauswahl hochladen.
. Falls GitHub automatisch Release Notes erzeugt, diese nur als Entwurf verwenden und fachlich prüfen. Sie ersetzen nicht die Informationen zu Artefakten, Einschränkungen und Upgrade-Hinweisen.
. **This is a pre-release** nur aktivieren, wenn die Version ausdrücklich eine Vorabversion ist.
. Solange noch geprüft wird, **Save draft** wählen. Erst nach der Kontrolle **Publish release** auswählen.

== GitHub-Release prüfen und veröffentlichen

Vor dem endgültigen Veröffentlichen prüfen:

* Der Titel des Releases enthält die richtige Version.
* Der Tagname entspricht exakt der Version und folgt dem Format `v<version>`.
* Der Tag zeigt auf den vorgesehenen Commit. Bei einem neu angelegten Tag dazu den ausgewählten Target-Branch und anschließend die Commit-Ansicht des Tags prüfen.
* Die Release Notes beschreiben das tatsächlich veröffentlichte Release.
* Alle erwarteten Assets sind vorhanden und sinnvoll benannt.
* Das Release ist nur dann als Pre-release markiert, wenn dies beabsichtigt ist.

Nach **Publish release** die fertige Release-Seite öffnen und mindestens Folgendes kontrollieren:

. Das Release ist über den richtigen Tag erreichbar.
. Die Assets lassen sich herunterladen.
. Die heruntergeladenen Dateien sind nicht leer und entsprechen den vorbereiteten Dateien.
. Versionsnummer, Release Notes und Asset-Namen stimmen überein.

Einen veröffentlichten Tag nicht nachträglich auf einen anderen Commit verschieben. Bei einem falschen Commit oder einem fehlerhaften Asset das Release nicht stillschweigend umdeuten. Stattdessen das Release nachvollziehbar korrigieren oder zurückziehen und erforderlichenfalls eine neue Version mit einem neuen Tag veröffentlichen.

[#website]
== Website aktualisieren

Nach der Veröffentlichung des GitHub-Releases wird die Website im Repository `j-specman/j-specman.github.io` aktualisiert. Dazu in den Klon dieses Repositorys wechseln, den Branch `main` auschecken und aktualisieren. Der Workflow `.github/workflows/pages.yml` baut daraus bei jedem Push auf `main` mit Maven (`mvn package`) die Website samt Online-Manual (aus `doc/specman-manual.adoc` des Specman-Repositorys) und Release-Historie und veröffentlicht sie über GitHub Pages. Dieselbe Maven-Konfiguration funktioniert auch lokal, siehe <<website-lokal-bauen,Website lokal bauen>>.

=== Release-Nummer prüfen

Prüfen, ob in der Website eine Release-Nummer steht, die angepasst werden muss, insbesondere in `index.html`, in `manual-theme/` und in `README.md`. Der Titel des Manuals kommt aus dem Manual selbst und braucht keine Anpassung. Stand Nov. 2026 steht die Release-Nummer aber nirgends in den statischen Inhalten der Web Site.

=== Manual-Quelle auf den Release-Branch umstellen

Wurde bei der Veröffentlichung ein neuer Release-Branch `<major>.<minor>.x` angelegt, muss die Manual-Generierung jetzt auf diesen Branch umgestellt werden. Auf `master` beginnt mit der Veröffentlichung die Weiterentwicklung des nächsten Releases, sein Stand ist nicht mehr stabil, und das Online-Manual soll das veröffentlichte Release beschreiben.

In `.github/workflows/pages.yml` im Schritt `Check out Specman (manual source)` den Wert `ref` ändern:

[source,yaml]
----
      - name: Check out Specman (manual source)
        uses: actions/checkout@v4
        with:
          repository: j-specman/specman
          ref: 1.4.x
          path: specman
----

Wurde kein neuer Branch angelegt (zum Beispiel bei einem Patch-Release, das auf einem bestehenden Release-Branch entsteht), bleibt `ref` unverändert.

Ab jetzt erscheinen Änderungen am Manual nur dann auf der Website, wenn sie auf den Release-Branch übernommen wurden.

=== Release Notes übernehmen

Die Website führt die Release-Historie (`releasenotes/index.html`). Ihre Quelle sind die Markdown-Dateien im Verzeichnis `releasenotes/` des Website-Repositorys.

Im Specman-Klon, der gerade auf dem neuen Release steht, liegen unter `releasenotes/` die Release Notes des neuen Releases und aller Vorgänger, die in diesem Branch enthalten sind. Sie werden in den Klon des Website-Repositorys kopiert, ohne dort schon vorhandene Dateien zu überschreiben. Dazu im Verzeichnis des Website-Klons ausführen:

[source,shell]
----
mvn antrun:run@collect-release-notes
----

Der Specman-Klon wird standardmäßig im Nachbarverzeichnis `../specman` erwartet. Liegt er woanders, wird der Pfad mit `-Dspecman.clone=<Pfad>` angegeben. Maven listet die kopierten Dateien auf. Gibt es keine neuen, wird nichts kopiert, das ist kein Fehler.

Kopiert werden nur Dateien, die im Website-Repository noch fehlen. Die Historie dort ist maßgeblich: Eine nachträglich korrigierte Datei darf nicht durch eine veraltete Fassung aus einem Release-Branch überschrieben werden. Nachträgliche Korrekturen an alten Release Notes werden deshalb im Website-Repository gemacht.

Anschließend zeigt `git status` im Website-Klon die neuen Dateien.

Auf diese Weise sammelt die Website jede neue Release-Notes-Datei ein, ohne dass die Dateien zwischen den Branches des Specman-Repositorys hin und her kopiert werden müssen.

[#website-lokal-bauen]
=== Website lokal bauen

Wer die Seiten vor dem Veröffentlichen lokal ansehen möchte, baut sie im Website-Klon mit:

[source,shell]
----
mvn package
----

Der Build braucht nur Maven, ein JDK (21 oder höher) und laufendes Docker. Asciidoctor und Pandoc laufen in Docker-Containern und müssen nicht installiert sein. Beim ersten Mal lädt Docker die Images, das dauert einige Minuten.

Das Ergebnis liegt in `_site/`: das Manual in `_site/manual/` (HTML und PDF) und die Release-Historie in `_site/releasenotes/`, jeweils mit `index.html` als Einstieg. Das Manual stammt aus dem Stand, der im Specman-Klon gerade ausgecheckt ist (standardmäßig `../specman`, sonst mit `-Dspecman.clone=<Pfad>` angeben). Der Workflow auf GitHub verwendet stattdessen den Branch aus `ref` in `pages.yml`.

=== Veröffentlichen und prüfen

. Den Workflow `Build and deploy website` auslösen. Er baut die Website samt Online-Manual und Release-Historie neu aus dem aktuellen Stand der Manual-Quelle. Das ist auch dann nötig, wenn an der Website selbst nichts zu ändern war, denn sonst zeigt das Online-Manual weiter den alten Stand.
** *Es gab Änderungen* (neue Release Notes, Release-Nummer oder Manual-Quelle umgestellt): Änderungen committen und auf `main` pushen. Der Push löst den Workflow automatisch aus. Bei einem neuen Release ist das der Normalfall, denn die neue Release-Notes-Datei ist mindestens neu dazugekommen.
** *Es gab nichts zu ändern:* Nichts einchecken, sondern den Workflow manuell starten. Dazu auf GitHub das Repository `j-specman/j-specman.github.io` öffnen, **Actions** wählen, in der Liste links den Workflow **Build and deploy website** auswählen, **Run workflow** öffnen, den Branch `main` auswählen und **Run workflow** bestätigen.
. Im Bereich **Actions** des Repositorys prüfen, dass der Lauf erfolgreich war.
. Das Online-Manual öffnen und prüfen, dass es den Stand des neuen Releases zeigt, zum Beispiel am Titel mit der Versionsnummer.
. Auf der Landing Page über die Kachel **Release history** die Release-Historie öffnen und prüfen, dass das neue Release oben in der Liste steht und seine Seite korrekt dargestellt wird.

[#aeltere-releases]
== Ältere GitHub-Releases nachträglich veröffentlichen

Für ein älteres Release wird derselbe GitHub-Ablauf verwendet. Vor dem Anlegen des Releases ist jedoch zusätzlich zu prüfen:

. Der historische Commit ist eindeutig identifiziert.
. Der Tag `v<version>` existiert noch nicht oder zeigt bereits auf genau diesen Commit.
. Die hochzuladenden Artefakte gehören nachweisbar zu diesem Commit und dieser Version.
. Nicht mehr eindeutig zuordenbare oder nicht vertrauenswürdig rekonstruierte Dateien werden nicht hochgeladen.

In den Release Notes muss kenntlich gemacht werden, dass das Release nachträglich angelegt wurde. Dabei sollten der historische Versionsstand und das Datum der nachträglichen Veröffentlichung genannt werden. Die automatische Erstellung von Source-Archiven durch GitHub ersetzt auch bei älteren Versionen keine verifizierten Release-Artefakte.
